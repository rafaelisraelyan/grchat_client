- **Видеозвонок больше не приходит как аудио (2026-10-13, ждёт живой проверки)**
  - Симптом: пользователь звонит по видео, у собеседника карточка
    «Входящий аудиозвонок». Разбор лога 05:05:44–05:06:31: ВСЕ профили
    камеры дают `camera probe ...: open ok, no frames` → лестница
    возвращала null → оффер уходил БЕЗ `m=video`, а тип звонка
    собеседник читает ровно из SDP (`_prepareIncoming`:
    `sdp.contains('m=video')`). Деградация была «честной», но путающей.
  - §call-type: видеозвонок остаётся видеозвонком. Если камера на
    наборе не открылась, `_addLocal` добавляет sendrecv-трансивер без
    трека — m-line остаётся в оффере, камера подключается позже.
    Состояние `cameraOff: true` + один тост «Камера сейчас занята —
    включите её во время звонка». В ответе трансивер добавляется
    только если у пира в оффере был `m=video` (answer не может
    добавлять медиасекции).
  - Тонкость: трек-less трансивер negotiates как `recvonly` — один
    `replaceTrack` прикрепил бы кадры и НИЧЕГО не отправил. Поэтому
    `_senderCanSendVideo()` проверяет `getCurrentDirection()` и при
    recvonly делает одну ренеготиацию (`_ensureVideoSends`).
  - §dial-camera-walk: на наборе, если выбранная камера не отдала
    кадров, обход остальных камер (физические первыми, максимум 3,
    короткая лестница из двух профилей), выбор сохраняется — следующий
    звонок стартует на рабочей камере. Тот же обход разрешён для
    «Автоматически» в настройках (устройство не названо — значит
    «любая рабочая»); названное устройство не подменяется никогда.
  - Бюджет «frameless»: открытие без единого кадра — ответ уровня
    УСТРОЙСТВА (забитый драйвер, чужой держатель, отключённая камера),
    а не профиля, поэтому лестница сдаётся после двух таких открытий
    (`CallState.ladderShouldStop`), тогда как «кадры ниже запроса»
    профиль и лестницу продолжает. Иначе набор на сломанной камере
    стоил 7.5 с, а с обходом — десятки секунд.
  - Слепой фоллбэк (без sourceId) теперь тоже проверяется кадрами:
    чёрный видеотрек хуже его отсутствия.
  - Логи читаемее: `camera probe [<устройство>] WxH@fps: ...`
    (`CallState.shortDevice` режет 90-символьные USB-пути); тосты про
    занятость больше не утверждают «другим окном grchat» — держателем
    может быть любая программа (у пользователя это NVIDIA Broadcast).

  1. Дефолт — первая ФИЗИЧЕСКАЯ камера: маркеры виртуальных

     дефолт (`resolveCameraId/resolveMicId`). Настройки: OBS-звёзды и
     промо-подсказка убраны, виртуальные помечены «(виртуальная)».
  2. Баннер низкого fps: чистый решатель `shouldShowCameraCapNotice`
     (потолок ≤ 20 fps, локальная камера включена, не шэринг, один раз за
     звонок; наличие второй камеры — только вариант текста). Плавающая
     карта в медиа-зоне (не snack и не диалог): кнопка «Настройки» →
     SettingsScreen, крестик. Чип «Камера: N fps» позже убран из UI
     (провайдер `cameraFpsCapProvider` тоже) — под капотом остались
     FpsCapLearn, floor и логи `camera fps cap:`/`camfps=`.
  3. Живая смена камеры/микрофона без перезвона: `switchCamera` /
     `switchMicrophone`. Контракт смены камеры — ЦИКЛ off → switch → on
     (подтверждён пользователем: драйверы не переключаются на лету, ручной
     маршрут «выключил камеру → выбрал другую → включил» работает):
     replaceTrack(null) → полный release старого захвата (stop ПЕРЕД
     removeTrack, §plugin-dispose-quirk) → открытие целевого устройства
     той же probe-лестницей → replaceTrack нового трека. CameraLock
     непрерывен у этого инстанса, окна перехвата нет. Тот же выключатель
     пользователя = реальный отпуск устройства (свет гаснет, чужие
     приложения могут взять камеру). Тот же выбор при выключенной камере
     сохраняет состояние «выключено». P2P: открытие с проверкой кадрами,
     replaceTrack на тот же сендер; при неудаче — старая камера остаётся,
     сохранённый выбор откатывается, короткая ошибка). CameraLock держится
     непрерывно одним владельцем (нет окна перехвата вторым инстансом и
     нет двойной блокировки). Обучение сбрасывается через публичный
     `resetCaptureLearning` (fps-потолок, чип-провайдер, высота, hold),
     тир пересчитывается под новый захват. LiveKit-сцены: штатная смена
     через `room.setVideoInputDevice / setAudioInputDevice` — в
     group_call и voice_state добавлены switchVideoDevice/switchMicDevice,
     настройки вызывают их, если P2P не активен. Выбор микрофона при
     старте звонка идёт тем же sourceId-путём (починено ранее); замена
     в звонке — replaceTrack того же аудио-сендера.
  4. Лог финал: `camera opened: label=<track.label>, requested=…,
     source=auto|explicit|walk|fallback, device=<getSettings().deviceId>`
     (device — не эхо; track.label у этого плагина — рандомный id трека,
     сохранён для трассировки), плюс `camera released: label=… (<путь>)`
     на каждый реальный отпущенный захват и
     `camera probe [<устройство>] WxH@fps: …` на каждую пробу.

- **Ed25519-подписи серверных конвертов (2026-10-13, v1.5.8-фича)** - полностью.

## Открыто

- **Вылеты звонка: корни и защита (14.10, проверено вживую)**
  - **§camera-busy — мой дефект, стоивший звонка.** При занятой
    `CameraLock` я разрешил обход камер («два окна держат две камеры»).
    Блокировка не привязана к устройству, поэтому обход брал именно занятую
    `Camera (NVIDIA Broadcast)`: второй граббер по DirectShow убивал пайплайн
    первого окна, ICE рвался через 56 мс, звонок падал. Правило: **при
    занятой блокировке не открывается ни одно устройство** — тост «Камера
    занята другим окном grchat», звонок жив. Обход остался только для
    чужих держателей (Broadcast) и только когда блокировка наша.
  - **§reconnect — машина состояний вместо реакции на разрыв.** Раньше на
    `iceConnection` не реагировал никто (только лог), а `pc connection`
    только вешал баннер. Теперь чистая `ReconnectWatch`: disconnected →
    «Переподключение…» + грейс 10 с; восстановление — та же сессия, таймер
    звонка не сбрасывается; истёк грейс → завершение с причиной
    (`call ended: reason=link-loss`); failed/closed — сразу.
  - **Таймер скоупится к (epoch, callId).** Поздний колбэк прошлого звонка
    не может завершить новый (`LinkVerdict.stale` не меняет состояние).
  - **Три заслона от поздних событий умирающего PC:** рост `_epoch` при
    закрытии транспорта; флаг `_tearingDown` на всё время `hangup()`
    (серверный round-trip асинхронен — события в этом окне игнорируются);
    проверка `identical(from, _pc)`, что событие пришло от текущего
    транспорта.
  - **§epoch-guard для камеры.** Проба занимает 1.5–3 с; если за это время
    звонок сменился, захват глушится (`stale camera capture released`), а не
    приклеивается к чужому `PeerConnection`. Проверки стоят после
    `getUserMedia`, после `replaceTrack` и в пути авто-восстановления.
  - **§call-type + связка.** Видеозвонок без камеры = m-line-пустышка,
    recvonly-ренеготиация при подключении камеры.
  - **Отладка без сети — хук, а не WiFi.** «Выключить WiFi» на одной машине
    не проверяет ничего: сигналинг идёт по loopback (`127.0.0.1:8443`),
    медиа — host-кандидат, а виртуальный адаптер (`172.19.0.1`, happ-xray)
    переживает отключение WiFi. В Настройках → debug-блок «Диагностика
    звонка»: обрыв 2 с / обрыв >10 с / сброс сразу — бьют по настоящему
    коду, воспроизводимо. Не попадает в релиз (`kDebugMode`).
  - Живая проверка 19:11: восстановление через 2.01 с, завершение ровно
    через 10.02 с, сброс — мгновенно, ни одного вылета.
