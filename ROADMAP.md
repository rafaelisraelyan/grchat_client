# GRChat — Roadmap до закрытой беты, Web и Mobile

> **Проектный документ / уточнённая редакция v2, 19.10.2026.**
> Дополнен сверкой с опубликованными GRChat Releases, клиентским `CHANGELOG.md` и серверным `PROTOCOL.md`.
> Репозиторий назначения: `grchat_client/ROADMAP.md`.
> Это **план**, а не акт технической приёмки. Не изменяет `BACKLOG.md`, `AGENTS.md` и серверный протокол.

## 1. Цель и принципы

**Ближайшая цель:** выдать небольшой группе друзей рабочую **закрытую Desktop Beta**, затем по результатам настоящего использования довести существующие функции, перейти к Web и после этого — к Android/iOS.

**Продукт:** личные и групповые сообщения; сообщества и каналы; личные и групповые звонки; постоянные голосовые комнаты; удобный интерфейс. Не добавлять новые крупные функции, пока текущий набор не стабилен.

**Приоритеты:** безопасность и сохранность пользовательских данных → базовая функциональность → корректное завершение при сбое → наблюдаемость и восстановление → удобство → расширение возможностей.

**Архитектура:** на этапе беты сохранить модульный Java 21 сервер + PostgreSQL, самостоятельный TCP/TLS JSONL transport, LiveKit SFU для групп/voice, P2P WebRTC для 1:1. Не переходить на микросервисы без измеренных причин. Заранее отделять клиентскую бизнес-логику от транспорта для будущего WSS/Web.

### Обозначения

- **P0 / Beta blocker:** без выполнения не приглашать внешних тестировщиков.
- **P1:** желательно закончить до беты; допускается известное ограничение с понятным обходом и диагностикой.
- **P2:** после начала закрытого тестирования.
- `TODO` — задача, требующая реализации или доказательной проверки; `VERIFY` — не утверждаем, что функция отсутствует; `DONE LOCAL / NOT MERGED` — подтверждено локальным отчётом, но отсутствует или не подтверждено в опубликованном `master`.
- Для закрытия каждого пункта хранить ссылку на commit/PR или тест/отчёт, дату и критерий PASS. Само наличие кода не означает PASS.

### 2A.4. Что релизные заметки НЕ доказывают

- Безопасность внешнего production-периметра, отсутствие plaintext listener и корректность боевых секретов.
- Проверенные бэкапы PostgreSQL **и** файлов с успешным restore.
- Полную E2EE с проверенным key management (не обещать функцию без отдельной проверки).
- Стабильность на разных сетях, через NAT/TURN, непрерывность реального RTP при ICE restart и glare.
- Безопасный multi-device voice reconnect, отсутствие ghost participants, готовность LiveKit WSS.
- Готовность браузерного/мобильного клиентов и доступность macOS-артефактов.

**Практический вывод:** не нужно заново реализовывать Mini Call, базовое окно звонков, адаптивное качество или проверку подписей. Нужно довести их до beta quality, синхронизировать ветки и закрыть P0 безопасность/восстановление данных/инфраструктуру/реальные сетевые проверки.

- [ ] **DATA-03** Тесты повторной доставки и дедупликации: reconnect, двойное нажатие Send, обрыв после записи сообщения, но до ответа; идемпотентность важна, если клиент повторяет запрос. Согласовать request IDs с server-side semantics.
- [ ] **DATA-04** Проверка транзакций для сообщений, вложений, инвайтов, ролей, удаления, reset-сессий; конкуренция двух устройств; безопасные миграции с планом отката/backup.

- [ ] **OPS-02** Health/readiness probes, graceful shutdown, ограничение ресурсов/рестарт-политика, реакция на заполненный диск/недоступную БД/SMTP/SFU; сервис должен отказать предсказуемо, а не портить состояние.

## 7. Этап B4 — звонки и voice для первой беты (P0)

**Принцип:** для беты не обязателен идеальный ICE restart во всех сетях, но обязательно отсутствие зависших звонков, потери управления, неправомерного восстановления и утечек устройств. Если восстановление не удалось — корректное завершение.

- [ ] **CALL-01** Завершить и интегрировать с regression gate локальные Stage 2A/2B, проверить server call ownership, authorisation `call_resume`, TCP/TLS reconnect, 10-секундный grace, multi-device и session reset.
- [ ] **CALL-02** Stage 2C: после R5.3 провести native glare-control (renegotiation без glare → одновременные offers → проверка RTP). **Не интегрировать непрошедший Perfect Negotiation.** Если rollback продолжает губить media, использовать безопасную pre-offer serialization после native доказательства.
- [ ] **CALL-03** Если ICE restart не готов к бете, ввести fail-safe политику на `ICE disconnected/failed/closed`: нет бесконечного ожидания/шторма, явный статус, корректное завершение и освобождение микрофона/камеры; не запускать restart на закрытом PC. Проверить две GUI-копии и RTP stats на реальных медиоустройствах.
- [ ] **CALL-04** Stage 2D / LiveKit: устранить userId-scoped `voice.leaveAll(userId)` при disconnect одной из сессий; связать presence с конкретным connection/session, reconnect и roster reconciliation, проверить ghost participants, server mute/limits и границы доступа.
- [ ] **CALL-05** На двух внешних сетях проверить 1:1 (аудио/видео) и SFU-группу/voice с доступным TURN и публичным LiveKit WSS, освобождение ресурсов после hangup, неуспешный звонок и повторный звонок.

## 8. Этап B5 — CI, сборки и запуск закрытой беты (P0)

- [ ] **REL-01** Серверный CI: Java 21 + PostgreSQL integration tests/Flyway + статический/зависимостный аудит. В серверном Dockerfile package запускается с `-Dmaven.test.skip=true`: тесты должны быть обязательным **отдельным CI gate** до сборки/publish образа.
- [ ] **REL-02** Клиентский CI: Windows build + Dart analyze/unit, macOS build/smoke (существующий macOS workflow запускается вручную), минимум один TLS integration suite. Не считать headless-тест заменой ручного media smoke.
- [ ] **REL-03** Подписанный desktop beta release и verified update/rollback (проверить весь путь v1.5.7 → новая бета; публичный v1.5.9/v1.5.10 release asset в проверенном списке отсутствовал). В релизе нет dev CA/debug secrets; проверить установку на чистой Windows и macOS (если macOS входит в первую бету); release number **строго выше** опубликованной версии клиента.
- [ ] **REL-04** Режим закрытого набора тестировщиков: аккаунты/инвайты, канал обратной связи, краткая инструкция, privacy notice, срок хранения логов и диагностика только с согласия, процесс сообщения об уязвимостях.
- [ ] **REL-05** Бета-план: 5–20 друзей (предложенный начальный масштаб), разные компьютеры/провайдеры; 1–2 недели наблюдения до расширения. Это не гарантия нагрузки, а первая ступень rollout.
- [ ] **REL-06** Incident playbook: кто получает сигнал, как выключить регистрацию/новую функцию, восстановить backup, откатить релиз, уведомить тестировщиков; проверить хотя бы одну репетицию.

### Release GO / NO-GO (закрытая beta)

**GO только когда:**

1. P0 периметр закрыт, TLS проверен извне, доступы/сессии авторизованы.
2. Backup БД и файлов + проверенный restore работают.
3. Критические пользовательские сценарии двух независимых аккаунтов пройдены.
4. При любых известных сбоях звонок не зависает навсегда, камеры освобождаются, voice presence согласован.
5. Сервер/клиент прошли regression CI, сборки подписаны, мониторинг и rollback готовы.
6. Все известные P0 дефекты закрыты; P1 ограничения задокументированы и объяснены тестировщикам.

**NO-GO:** незашифрованный публичный transport; нарушение изоляции аккаунтов; потеря/порча сообщений; невосстановимые базы/вложения; безусловный crash loop; известный невосстановимый capture/device leak; невалидные обновления; невозможность расследовать инцидент.

## 12. Что специально НЕ делаем до beta

- Не переписываем весь сервер на микросервисы.
- Не переписываем транспорт ради Web до проверенного Desktop beta, но сохраняем абстракцию для расширения.
- Не внедряем непроверенные SDP glare/ICE recovery механизмы.
- Не обещаем end-to-end encryption, если нет доказанного ключевого обмена и threat model.
- Не добавляем Bot API, широкий каталог функций, монетизацию и сложный маркетплейс до обратной связи с друзьями.
- Не ставим «идеальное восстановление медиапотока на любой сети» условием закрытой beta; ставим **безопасное и конечное** поведение.

## 13. Следующие 5 инженерных действий

1. Сверить и сохранить локальные Stage 1.1/2A/2B/2C с текущими ветками; определить процедуру интеграции без потерь.
2. Исправить/доказательно закрыть публичный plaintext listener и выполнить сетевую проверку TLS/LiveKit/TURN.
3. Добавить backup PostgreSQL+files и провести реальный restore rehearsal.
4. Пройти сквозную beta E2E-матрицу auth → DM → канал → вложение → P2P → voice на двух устройствах/сетях.
5. Включить CI, мониторинг, подписанную beta-сборку и собрать первую маленькую группу друзей.
